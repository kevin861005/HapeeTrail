# 顏色與樣式對照表（`color` / `style`）

> **本檔由 iOS 維護。** 後端不實作、不驗證、不做任何同步檢查——它只儲存代號，
> 不理解代號的語意。這份文件存在的唯一理由是：在資料庫裡看到 `color = 3` 時，
> 後端 debug、客服回報與資料分析查得到它代表什麼，也才能重建歷史版本。
> 每次追加項目時，由 iOS 在同一個 PR 更新本檔。

## ⚠️ 硬性約定：代號是永久 ID，不是清單位置

這是整個設計唯一會**損壞歷史資料**的失效模式，先讀完再往下看。

1. **對照表只能追加新項**，新項用下一個沒被用過的代號。
2. **既有代號的意義永久凍結**——`1` 一旦是黃色就永遠是黃色，不因為調色盤重排而改變。
3. **顯示順序由 client 決定，必須與代號身分脫鉤**：要怎麼排、哪個放第一個，
   是呈現層的自由；但排序不得決定代號，代號也不得跟著排序走。
4. 停用某一項時**代號保留、不再發放，且不得回收給別的顏色**——
   已經留在便條上的舊代號仍需渲染得出東西。

**違反的後果**：若在對照表中間插入一個新顏色並讓後面的項目順移，
**所有既有便條會靜默換色**。而對照表在裝置端、後端看不到它變了，
兩側都不會產生任何錯誤訊號——沒有 migration 失敗、沒有 API 錯誤、沒有 log。
等旅人回報「我的便條顏色不對」時，已經沒有原始資料可以還原是哪個代號對到哪個顏色。

後端在技術上無法對此把關（它不知道對照表長什麼樣），**只能靠紀律**。

## 值域與未知代號

- `color` 與 `style` 是**兩個各自獨立**的小整數代號，從 `1` 起算，不打包成單一數字。
- 後端只做**範圍**粗檢：`1`–`32767` 之外 → `invalid_style_code`。
  範圍內但不在本表的代號**會被接受、原樣儲存、原樣回傳，且不會有任何錯誤訊號**。
- 因此 **client 遇到未知代號一律渲染預設樣式**（`color = 1` / `style = 1` 的外觀），
  不得視為錯誤、不得破圖。這讓後端新增顏色不必等 app 發版，
  也讓舊版 app 看得懂新便條——見 [`notes.md`](notes.md) §9「未知值政策」。

| 1 | 黃色 | 伺服器預設值（`p_color` 省略時） |

## style — 卡片樣式

| 代號 | 名稱 | 備註 |
|---|---|---|
| 1 | 預設便條紙 | 伺服器預設值（`p_style` 省略時） |

> 上表只列了目前已凍結的兩個代號（`1` 是伺服器預設值，必須指向一個具體項目、
> 不是「代表預設」的抽象槽）。其餘項目由 iOS 追加。
> 追加時請一併寫上追加日期，方便日後對照歷史資料。
