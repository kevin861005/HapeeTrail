# ADR-0009：全空白內容的判定範圍，以及刻意不追的那條線

日期：2026-07-29　狀態：已採納（T16 實作）

## 決策

`drop_note` 的內容以 `regexp_replace(content, '^\s+|\s+$', '', 'g')` 正規化，
trim 後為空即 `content_empty`。字元集是 Unicode 的 White_Space 加上 U+001C–U+001F。

**格式字元不追**：零寬空白（U+200B–200D）、word joiner（U+2060）、BOM（U+FEFF）、
U+180E 在 Unicode 裡是格式字元而非空白，因此只由它們組成的便條建得起來。

## 理由

- 原本的 `btrim(content)` 只剝 U+0020 一個字元——連 tab 與換行都不剝，更別說全形空白。
  於是 `　　`（U+3000）能建立一張在地圖上看起來空白的便條，而兩側都不會有錯誤訊號。
  CJK 使用者按到全形空白鍵並不罕見，這是**常見的意外**，值得擋。
- 同時對齊 client：各平台慣用的「whitespaces and newlines」與 UTF-8 locale 下的 `\s`
  幾乎同一套，兩邊不一致的症狀是「app 預檢說可以送、伺服器回 `content_empty`」。

## 為什麼停在這裡

追格式字元會踏進一條沒有終點的路：剝完 Cf 類別，還有變體選擇符、組合字元、
只由標點組成的內容⋯⋯**「看起來是空的」沒有可判定的邊界**。而且愈修愈長的字元集，
每一項都是與 client 預檢邏輯產生分歧的新機會。

所以這裡的分界是**意外 vs 刻意**：伺服器擋使用者不小心送出的空白內容；
刻意做出來的空白便條屬於內容濫用，該由檢舉機制（T3）處理，不是靠 trim 的字元集。

## 已知環境依賴

`\s` 涵蓋 U+3000／NBSP **取決於資料庫的 ctype**——`C` locale 下會退化成只認
U+0009–000D 與 U+0020，本次修正對頭號情境（全形空白）就靜默失效了。

靠人記得在部署後檢查守不住，所以 migration **在套用時就驗**：ctype 不支援即拋例外、
`db push` 大聲失敗，而不是安靜地上線。測試套件另有 U+3000 與 NBSP 的 fixture，
hosted 上若真的退化會直接變紅。

真撞到的退路：把 `\s` 換成顯式字元集的 `btrim`——確定、與 locale 無關，
代價是要自己維護那份 Unicode 空白清單。
