# ADR-0004：列表分頁採不透明游標

日期：2026-07-28　狀態：已採納（T11-03 實作）

## 決策

兩支列表 RPC 的分頁參數從「排序鍵 ＋ id」兩欄位收斂為**單一不透明字串** `p_cursor`；
回傳改為 `{ items, nextCursor }` envelope，`nextCursor` 為 null 是唯一的終止訊號。
client 的義務只剩「原樣回傳」，游標內部結構不屬於契約。

## 理由

- v2 把排序鍵（timestamptz ＋ uuid）直接暴露在 API 上，於是契約必須要求 client
  「時間戳 byte-for-byte 原樣回傳」——經過日期型別轉換會丟失微秒精度、翻頁靜默掉列。
  這是把後端的實作細節變成 client 的義務，且失敗時沒有訊號。
- 兩個欄位必須成對出現，只帶一個就是 client bug；收斂成一個參數後這類 bug 不可能寫出來。
- 排序策略日後要換（距離／熱門／推薦）時，API 形狀不必動。
- 以空陣列作為終止訊號會逼 client 為了確認結束多打一次；`nextCursor: null` 省掉那一趟。

## 實作

- 游標 ＝ base64(JSON{`v` 版本, `k` 排序鍵名, `t` 排序鍵值, `i` id})，編解碼各只有一處
  （`as_cursor` / `parse_cursor`）。
- **雙閘門**：`v` 擋編碼格式變更，`k` 擋排序語意變更。`k` 同時讓兩支列表的游標無法互換——
  否則 my_collection 的游標會被 my_notes 拿去跟 `created_at` 比較，靜默回錯頁而毫無訊號。
  （此缺陷由 T11-03 的 code-review 抓到，`k` 是修正。）
- 任何解碼／版本／排序鍵失敗一律拋 `invalid_cursor`，**不靜默退化**成第一頁——
  靜默退化的兩種結局是掉列與無限翻頁，兩者都比大聲失敗難查。
- **不簽章、不加密**：游標不授予任何權限，查詢永遠限縮在呼叫者自己的資料範圍內
  （RLS ＋ where），竄改最多只能改變自己看到的起點。加簽章是沒有威脅模型支撐的複雜度。
  升級訊號：哪天游標開始編碼「跨使用者」的查詢條件，就必須加簽章。
- 排序規則不變：（排序鍵, id）複合比較處理同刻平手。
