# ADR-0006：私人便條（`audience`）的可見性與撿取回應

日期：2026-07-28　狀態：已採納（T11-05 實作）

## 決策

便條帶 `audience`，值為 `anyone`（預設）與 `self`（只給自己的旅遊紀錄）。
`self` 的便條：不出現在**任何人**的探索結果（含作者自己）、任何人都撿不走、
**不計入未撿便條的數量上限**。

## 理由

- 產品要支援第二種使用方式：把旅程記錄下來，而不只是留給陌生人撿。
- 私人便條永遠不會被撿走，若計入 50 張未撿額度，認真記錄旅程的旅人很快會撞上一個
  本來是為了防濫用而設的限制。

## 關鍵取捨

- **他人嘗試撿一張私人便條時回 `note_not_found`，刻意不新增 token。**
  新增一個「這是私人便條」的錯誤等於向外人確認：該座標存在一張他看不到的便條。
  對外人的回應必須與「便條不存在」**完全相同**。
- **`audience` 用 `text` ＋ CHECK，不用 Postgres enum 型別**：enum 加值有交易限制、
  刪值幾乎不可能，而這個欄位的前提就是日後會加值（如 `close_friends`）。
- **`audience` 不套用「未知值走預設」政策**（ADR-0005 的 `color`/`style` 套用）。
  不認得的值一律拒絕（`invalid_audience`）。理由：它是後端必須理解才能過濾的業務語意，
  不是純呈現；靜默走預設會把使用者以為私密的便條變成公開的，而使用者收不到任何訊號。
  此後新增請求端 enum 一律比照判準：**純呈現走預設，影響可見性的拒絕。**

## 實作

- 探索用的部分索引，其條件加入 `audience = 'anyone'`——私人便條永遠不進探索結果，
  排除在索引外可讓熱查詢的索引更小，且索引條件與查詢條件一致才會被計畫採用。
  實測同資料前後對比：計畫形狀不變、候選列 143 → 120。
- 未撿便條上限的計數同樣加上 `audience = 'anyone'` 條件。
