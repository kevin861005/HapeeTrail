# ADR-0010：便條 90 天後退出地圖，過期以讀時推導

日期：2026-07-29　狀態：已採納（T4 實作）

## 決策

**未撿的公開便條**在建立 90 天後退出探索與撿取。過期是**讀時推導**的
（`created_at + public.note_ttl()`），不是儲存的狀態——沒有 cron、沒有 `expired_at` 欄位。

- 不進探索結果；撿取回 `note_not_found`；不再計入未撿便條的額度
- **仍留在作者的 `my_notes` 裡**，不會憑空消失
- wire 新增 `expiresAt`（推導值）：公開便條 ＝ `createdAt` ＋ 90 天，**旅遊紀錄為 null**

**已撿走的便條與旅遊紀錄不會過期**。前者在別人的收藏裡，刪它是毀別人的東西；
後者是使用者的私人紀錄，刪它是資料遺失。

## 為什麼是讀時推導，不是 cron

spec 對狀態欄位的規定是「必須由伺服器推導而非儲存」，這裡正好適用：過期完全由
`created_at` 決定，落地成欄位會產生第二個真相來源，還多一個會失敗的活動元件。
讀時推導的三個實際好處：零新增基礎設施、不碰任何一列既有資料、期限可以調整而不必回填。

代價（已接受）：過期列永遠留在儲存與探索的熱索引裡。partial index 的述詞必須 IMMUTABLE，
塞不進 `now()`，所以 TTL 只能當查詢條件，索引篩不掉它們。**升級路徑**是等索引真的大到有感，
再加一支 cron 把「早就過期又沒人撿」的列刪掉——那時它才真的是「一句 delete」，
而且不必動任何查詢邏輯。

## 為什麼過期便條仍留在 my_notes

spec user story 13：「我想在翻閱自己的便條時不會有便條莫名消失，好讓我信任這份紀錄是完整的。」
硬刪除會正面撞上這條。作者看得到自己留過什麼，只是它不再在地圖上——這也讓
`expiresAt` 有意義（app 可以顯示「已過期」或倒數）。

## 為什麼過期便條的撿取回 `note_not_found`

與私人便條同一個立場（ADR-0006）：它已退出地圖，沒有理由讓外人分辨「這裡曾經有一張」
與「這裡什麼都沒有」。不新增 token。

註：過期**且已被撿走**的便條仍回 `note_taken`，因為它離開地圖的原因是被撿走
（ADR-0001 的獨佔語意），而「有人搶先一步」對 UI 是有意義的訊號。兩種離開地圖的方式
給不同答案是刻意的。

## client 的判準

「這張還在地圖上嗎」＝ `pickedUpAt == null && now < expiresAt`——**兩個欄位都要看**。
在此之前 `pickedUpAt == null` 單獨就夠，TTL 讓那個推論失效，所以 `expiresAt` 必須上 wire。

期限是伺服器常數，**client 不得硬編 90 天**（與「不得硬編 50m/100m 半徑」同一原則）：
調整期限不需要 app 改版。`note_ttl()` 因此也不授權給任何 client 角色。

## 已知天花板（已量化）

便條密度極端集中時查詢計畫會變：10 萬張便條散在全球時，探索仍走
`notes_active_location_gix` 的 Index Scan、TTL 落在 Filter（0.05–0.08ms）；
但同樣 10 萬張全擠在 0.03 度的方框內時，planner 改用 BitmapAnd 併入 `notes_author_ix`
掃 `created_at`（105218 列），51.9ms vs 17.9ms。熱門景點真的長到那個密度時，
解法是讓過期列離開資料表，而不是動查詢。
