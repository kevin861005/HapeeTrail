# Spec：便條 API 契約 v3

Ticket: T11
日期：2026-07-28
設計背景：`docs/tasks/T11-contract-v3-design.md`（15 條已定原則與理由）

## Problem Statement

iOS 夥伴即將開始串接第一階段便條後端，但目前的 v2.1 契約有三類問題。

**產品能力不足**：每張便條長得一模一樣——旅人無法用顏色表達心情，也無法選擇不同的
便條紙樣式。更重要的是，旅人只能留下「給陌生人撿」的便條，沒有辦法留下**只給自己的
便條**當作旅遊紀錄；而這正是產品想支援的第二種使用方式。

**契約有會割傷 client 的銳角**：分頁游標把排序鍵（timestamp ＋ id）直接暴露在 API 上，
契約文件因此不得不用一整段警告 client「時間戳必須 byte-for-byte 原樣回傳，經過日期型別
轉換會丟失微秒精度，翻頁會靜默掉列」——這是把後端的實作細節變成 client 的義務。
同樣地，游標兩個欄位必須成對出現，只帶一個就是 client bug；翻到最後一頁必須再多打一次
拿到空陣列才知道結束；業務錯誤無法附帶任何資料，所以「再走近一點」的文案只能沿用上一次
探索結果的距離，而不是伺服器當下算出來的真實距離。

**後端有一個會隨時間變危險的寫法**：RPC 的回傳形狀是用「整列轉 JSON 再減掉幾個欄位」
產生的，也就是黑名單。往後每在便條表加一個欄位，預設都會直接出現在 wire 上，除非有人
記得回來減掉它。隨著檢舉旗標、TTL、作者資訊等欄位陸續加入，這個寫法遲早會洩漏不該
上 wire 的東西。

由於 iOS 尚未開始串接，現在是唯一可以無痛做破壞性修正的時機。

## Solution

在 iOS 動工前一次到位地發布契約 v3，包含兩件事。

**新增產品能力**：便條帶 `color` 與 `style` 兩個獨立的數字代號，實際的顏色與卡片樣式
對照表放在裝置端，後端只儲存代號、不理解其語意——如此新增顏色或樣式完全不需要後端
migration 或發版。便條另外帶 `audience`，區分「給任何人撿」與「只給自己的旅遊紀錄」；
私人便條不會出現在任何人的探索結果中，也不佔用未撿便條的數量上限。

**收掉契約的銳角**：分頁改用不透明游標字串，client 只需原樣回傳，排序策略日後可改而
不動 API 形狀，微秒精度的陷阱隨之消失；列表與探索結果一律包成 envelope 並以
`nextCursor` 為 null 明確表示結束；業務錯誤可附帶結構化資料，讓提示文案顯示伺服器
當下算出的真實數字；回傳形狀改為明列欄位的白名單，新增表欄位預設不上 wire；
時間戳格式固定；鍵名改為貼合 client 的 camelCase，座標改為巢狀物件。

同時把「未知欄位忽略、未知 enum 值與未知代號走預設」寫進契約本文，讓此後絕大多數的
新增都是非破壞性變更。

## User Stories

### 旅人（app 使用者）

1. 作為旅人，我想在留下便條時選擇顏色，好讓便條能表達我當下的心情。
2. 作為旅人，我想在留下便條時選擇便條紙的樣式，好讓我的便條有辨識度。
3. 作為旅人，我想在地圖上一眼看出附近的便條長什麼樣，好讓我決定要不要走過去撿。
4. 作為旅人，我想撿到便條時看到原作者選的顏色與樣式，好讓我感覺收到的是那個人親手做的卡片。
5. 作為旅人，我想留下只有自己看得到的便條，好讓我把這趟旅程記錄下來。
6. 作為旅人，我想確定我的私人便條不會被任何陌生人撿走，好讓我安心記錄私密的事。
7. 作為旅人，我想讓私人便條不佔用「未撿便條」的數量上限，好讓我可以長期持續記錄旅程而不會撞到為了防濫用而設的限制。
8. 作為旅人，我想在自己的列表裡分辨哪些是公開便條、哪些是旅遊紀錄，好讓我一眼看懂。
9. 作為旅人，我想在走太遠撿不到時看到還差多少距離，好讓我判斷要不要再走幾步。
10. 作為旅人，我想在內容超過字數時知道上限是多少，好讓我知道要刪掉多少字。
11. 作為旅人，我想在未撿便條達到上限時知道上限數字，好讓我理解為什麼不能再留。
12. 作為旅人，我想在撿取過於頻繁被擋下時知道大概要等多久，好讓我不必盲目重試。
13. 作為旅人，我想在翻閱自己的便條時不會有便條莫名消失，好讓我信任這份紀錄是完整的。
14. 作為旅人，我想在翻到最後一頁時立刻知道沒有更多了，好讓 app 不用多轉一次載入圈。
15. 作為旅人，我想在 app 更新前就能看到後端新增的顏色不會讓便條破圖，好讓我不必為了看便條而被迫更新。

### iOS 開發者

16. 作為 iOS 開發者，我想一次拿到完整且不會再變動的契約，好讓我可以放心開始串接。
17. 作為 iOS 開發者，我想不必等設計交出色票就能開始串接，好讓我的工期不被設計卡住。
18. 作為 iOS 開發者，我想收到巢狀的座標物件，好讓它直接對應到平台的座標型別。
19. 作為 iOS 開發者，我想時間戳格式永遠一致，好讓我不必為了小數秒位數寫容錯分支。
20. 作為 iOS 開發者，我想游標是一個不透明字串，好讓我不必理解也不會不小心破壞它的內部結構。
21. 作為 iOS 開發者，我想分頁只有一個游標參數，好讓我不會寫出「只帶一半」的 bug。
22. 作為 iOS 開發者，我想有明確的分頁終止訊號，好讓我的無限捲動邏輯單純。
23. 作為 iOS 開發者，我想知道遇到不認識的顏色或樣式代號時該怎麼辦，好讓我的渲染永遠有 fallback。
24. 作為 iOS 開發者，我想確定後端加欄位不會讓我的解碼失敗，好讓後端可以獨立演進。
25. 作為 iOS 開發者，我想錯誤碼是穩定的字串 token，好讓我可以安全地寫 switch。
26. 作為 iOS 開發者，我想在錯誤裡拿到實際數字，好讓提示文案顯示真實距離而不是估計值。
27. 作為 iOS 開發者，我想列表與探索結果都是物件而非裸陣列，好讓後端日後加欄位不會改變我的型別。
28. 作為 iOS 開發者，我想有一份匯入即可跑的 Postman collection，好讓我在寫程式前先看懂每個呼叫的實際樣子。
29. 作為 iOS 開發者，我想契約文件不含任何 client 語言的程式碼，好讓實作決定完全由我這邊做。

### 後端維護者

30. 作為後端維護者，我想在便條表新增欄位時預設不會外洩到 wire，好讓我不必依賴記憶力來維護隱私。
31. 作為後端維護者，我想新增顏色或卡片樣式時完全不需要改後端，好讓設計的迭代不經過我。
32. 作為後端維護者，我想日後改變列表排序策略時不必改變 API 形狀，好讓推薦或熱門排序可以無痛導入。
33. 作為後端維護者，我想在資料庫裡看到代號時查得到它代表什麼，好讓我能 debug、回應客服、做資料分析。
34. 作為後端維護者，我想地理查詢確定走索引，好讓便條量成長後探索仍然夠快。
35. 作為後端維護者，我想契約的三份產出（規格、語意文件、Postman）永遠同步，好讓 iOS 不會讀到互相矛盾的說法。

### 設計師

36. 作為設計師，我想新增顏色時只要更新裝置端對照表，好讓我不必排後端的工。
37. 作為設計師，我想既有代號的意義永久凍結，好讓我調整選色器的排列順序時不會改變旅人已經留下的便條長相。

## Implementation Decisions

### 便條資料模型

- 便條表新增三個欄位：`color`、`style`、`audience`。
- `color` 與 `style` 是**兩個獨立的小整數**，代表裝置端對照表的項目代號。不得打包成
  單一數字（如 `12` 代表色 1 形 2）——打包會讓「新增第三個樣式軸」與「某軸超過 9 項」
  雙雙變成破壞性變更。
- 代號**從 1 起算**，伺服器預設值指向對照表中一個具體項目（現行黃色 ＝ 1），不得保留
  一個「代表預設」的抽象槽。
- 後端**不驗證代號的語意合法性**，只做型別與範圍粗檢（小整數、大於等於 1）。後端維護
  一份合法值清單等於養第二份對照表，一定會跟裝置端漂移。連帶接受：client 必須對未知
  代號渲染預設樣式；且錯誤的代號會被靜默接受（iOS 若有 bug 送出超出範圍的值，該便條在
  所有裝置上永遠顯示預設樣式，且不會有任何錯誤訊號）。
- `audience` 是字串而非代號，值為 `anyone` 與 `self`，以 CHECK 約束。它與 color/style
  性質不同：它是**後端必須理解並據以過濾**的業務語意，不是純呈現。
- `audience` 使用文字型別加 CHECK，不使用資料庫的 enum 型別——enum 加值有交易限制、
  刪值幾乎不可能，而這個欄位的前提就是日後會加值。
- 既有列以預設值回填（`color` ＝ 1、`style` ＝ 1、`audience` ＝ `anyone`）。

### wire 格式

以下形狀是契約本體，比散文更精確地編碼了決定：

**便條**（留下、撿起的回傳，也是兩個列表的 item）

```json
{
  "id": "5f8f1c1e-…",
  "content": "今天的風很舒服",
  "color": 1,
  "style": 1,
  "audience": "anyone",
  "coordinate": { "latitude": 25.065472, "longitude": 121.533397 },
  "createdAt": "2026-07-23T10:00:00.123456Z",
  "pickedUpAt": null
}
```

**探索提示**（刻意不含內容與作者；帶 color/style 供地圖 pin 渲染）

```json
{
  "id": "5f8f1c1e-…",
  "color": 1,
  "style": 1,
  "coordinate": { "latitude": 25.06597, "longitude": 121.5334 },
  "distanceM": 30,
  "pickable": true,
  "createdAt": "2026-07-23T10:00:00.123456Z"
}
```

**列表與探索的 envelope**

```json
{ "items": [ … ], "nextCursor": "eyJ2IjoxLCJ0IjoiMjAyNi0…" }
```

探索結果無分頁，只有 `items`。裸陣列日後要加欄位是破壞性變更，故一律包成物件。

**業務錯誤**

```json
{ "code": "P0001", "message": "too_far", "details": "{\"distanceM\": 87}", "hint": null }
```

- 鍵名一律 camelCase，**縮寫視為普通單字**（`distanceM`、日後的 `photoUrl`，不是 `photoURL`）。
- enum 值與錯誤 token 一律小寫底線（與已凍結的錯誤 token 同一套）。
- 時間戳固定為 `YYYY-MM-DDTHH:MM:SS.ffffffZ`——永遠六位小數、永遠 `Z`。
- 請求 body 的鍵名維持 `p_` 開頭的底線命名，因為 PostgREST 規定 body 鍵名等於函式參數名。
  座標在請求端維持兩個獨立的浮點數參數而非巢狀物件：它們是**函式參數**，扁平才拿得到
  資料庫的型別檢查；回應端的座標是會長大的**資料物件**，故巢狀。兩者形狀不同是刻意的。

### 回傳形狀的產生方式

- 所有 RPC 的 JSON 一律**明列欄位建構**（白名單），取代現行的「整列轉 JSON 再減欄位」
  （黑名單）。這是本次變更中唯一有安全含意的部分：黑名單讓往後每個新增的表欄位都預設
  上 wire，白名單讓它們預設隱形。
- 便條與探索提示的形狀各自只在一處建構，五支 RPC 共用，避免形狀在不同 RPC 間漂移。

### 分頁

- 兩支列表 RPC 的三個游標參數（筆數上限、排序鍵、id）收斂為兩個：筆數上限與單一
  不透明游標字串。
- 游標內容為 base64 編碼的 JSON，含版本號、排序鍵值與 id。版本號讓日後更換排序策略
  （距離、熱門、推薦）時能辨識並拒絕舊游標，而不必改變 API 形狀。
- 游標**不簽章、不加密**：它不授予任何權限，查詢永遠限縮在呼叫者自己的資料範圍內，
  竄改游標最多只能改變自己看到的起點。加簽章是沒有威脅模型支撐的複雜度。
- 無法解碼或版本不符的游標一律拋出既有的 `invalid_cursor` token；靜默退化會掉列或
  無限翻頁，必須大聲失敗。
- `nextCursor` 為 null 表示沒有更多；不再以「回傳空陣列」作為終止訊號。
- 排序規則不變：我的便條依建立時間新到舊、我的收藏依撿起時間新到舊，皆以
  （排序鍵, id）複合比較處理同刻平手。

### 錯誤

- 業務錯誤仍為 HTTP 400 加 `P0001`，`message` 仍是唯一的判斷依據，token 字串維持凍結。
- 新增的 `details` 欄位由資料庫例外的 DETAIL 承載。**實測確認（2026-07-28，本機
  PostgREST）：`details` 是一個內容為 JSON 的字串，不是巢狀物件**——PostgREST 將
  DETAIL 原樣當字串傳遞。client 需對它做第二次 JSON 解析，且必須把解析失敗視為
  「沒有附帶資料」而非錯誤。
- `details` 為選配，可能為 null，client 不得依賴其存在。首批附帶資料的 token：
  距離不足附實際距離、內容過長附上限、便條數達上限附上限、撿取過頻附建議重試秒數。

### 探索與私人便條的互動

- 探索結果排除 `audience` 為 `self` 的便條——對所有人，包含作者自己（作者的便條本來
  就不出現在自己的探索結果中）。
- 他人嘗試撿取一張私人便條時回 `note_not_found`，**不新增錯誤 token**：新增一個
  「這是私人便條」的 token 等於向外人確認該座標存在一張他看不到的便條。
- 未撿便條的數量上限只計算 `audience` 為 `anyone` 的便條。私人便條永遠不會被撿走，
  計入的話會讓認真記錄旅程的旅人撞上一個原本為了防濫用而設的限制。

### 函式簽名與權限

- 五支 RPC 的回傳型別都會改變（列表與探索從回傳資料表改為回傳單一 JSON envelope），
  因此**必須先移除舊函式再建立**，不能就地取代；移除後需重新套用權限收回與授予。
- 現有的權限分工維持不變：三支寫入型 RPC 為 SECURITY DEFINER，兩支列表 RPC 為
  SECURITY INVOKER（權限由 RLS 與資料表授權把關，函式本身不越權）。
- 所有函式維持空的 search_path 與 schema 限定引用；每支逐一從 public 與匿名角色收回
  執行權後再授予已認證角色。

### 索引

- 探索用的部分索引，其條件加入 `audience` 為 `anyone`——私人便條永遠不會出現在探索
  結果中，把它們排除在索引外可讓熱查詢的索引更小，且條件與查詢一致才能被查詢計畫採用。
- 其餘索引不變。

### 契約產出物

- 三份產出必須同步更新：OpenAPI 規格（wire format 的權威）、語意文件（規則與 curl
  範例，維持語言中立、不含任何 client 語言程式碼）、Postman collection 與環境檔。
- 語意文件新增「未知值政策」一節：未知欄位忽略、未知 enum 值與未知代號走預設。
- 語意文件刪除已不適用的內容：游標必須 byte-for-byte 原樣回傳的警告、游標兩欄位必須
  成對的規則、以空陣列作為終止訊號的說明、時間戳小數秒位數可變的警告、
  「不得解析錯誤字串取數字」的替代做法說明。
- 新增一份**顏色與樣式對照表文件**放在 API 文件目錄下。它是純文件，後端不實作、
  不驗證、不做同步檢查；由 iOS 在每次追加項目時更新。沒有它的話，後端 debug、
  客服回報與任何資料分析都無從查起，也無法重建歷史對照表版本。
- 契約變更政策不變：錯誤 token 字串永久凍結，新增為非破壞性，改名或刪除為破壞性
  變更並須取得 iOS 簽核。

## Testing Decisions

好的測試只驗證**外部可觀察的行為**——呼叫某個 RPC 會得到什麼形狀、什麼錯誤 token、
什麼權限結果——不驗證函式內部怎麼組出這個結果。因此本次所有斷言都下在 RPC 的
呼叫邊界與 HTTP 邊界，不對 JSON 建構的實作方式、游標的內部編碼細節做斷言
（游標只驗證「原樣回傳可以翻頁、竄改會被拒絕」這個外部行為）。

沿用現有的**兩個 seam**，分工如下。

### Seam A：SQL／RPC 邊界（主力測試套件）

現有的行為驗證套件即為 prior art：整份腳本在單一交易內執行、結尾回滾不留資料；
以一個小工具函式設定 JWT claims 來模擬登入指定使用者；以另一個小工具函式斷言某段
SQL 會拋出指定的錯誤字串。跨使用者的 id 查詢必須先以資料庫超級使用者身分取得並存入
連線變數，再登入目標使用者斷言——否則 RLS 會讓查詢拿到空集合，測試變成空測
（此陷阱在 T1 的複核中實際發生過，測試檔開頭已有註記）。

此 seam 涵蓋：

- 便條與探索提示的 JSON 形狀（鍵名完全相符、且不含身分欄位與內部欄位）
- 座標巢狀結構與時間戳格式
- 三個新欄位的預設值、範圍粗檢、以及超出對照表範圍的代號被接受
- 私人便條不出現在任何人的探索結果、他人撿取回 `note_not_found`
- 私人便條不計入未撿便條上限
- 全部錯誤 token 與新增的 `details` 內容
- 不透明游標的往返翻頁（含所有時間戳同刻的最嚴苛平手情境——測試在單一交易內，
  時間函式恆定，天然構成此壓力測試）、竄改與版本不符的游標被拒絕、
  `nextCursor` 在最後一頁為 null
- RLS 與角色權限（匿名角色不可達、空 claims 回防禦碼）
- 既有的反濫用上限與獨佔撿起、冪等重試行為未被本次變更破壞
- 地理查詢的查詢計畫確認走索引（專案守則要求地理查詢必須以 EXPLAIN 驗證）

### Seam B：HTTP／PostgREST 邊界（wire 驗證）

現有的 Postman collection 以 newman 執行即為 prior art（T9 已驗證可跑）。此 seam
只加入**在 SQL 邊界之下看不到**的少量斷言，不重複 seam A 的覆蓋：

- 鍵名確實以 camelCase 抵達，座標確實是巢狀物件
- 業務錯誤的 `details` 確實出現在回應 body，且確實是字串而非物件
- 不透明游標經過完整 HTTP 往返後仍可用於翻頁
- HTTP 狀態碼與兩層錯誤閘門的分界

此 collection 同時是交付給 iOS 的範例，因此斷言要精簡、資料夾順序即為完整流程、
token 由 script 自動帶入的既有設計維持不變。

### 測試環境注意事項

新增或移除函式後，PostgREST 的 schema cache 不會自動更新，直接呼叫會得到 404 而非
預期結果（2026-07-28 實測）。任何跨 HTTP 的驗證步驟前必須先觸發 schema 重載，
否則會誤判為實作錯誤。

## Out of Scope

以下**刻意不納入**本次變更。它們日後加入時都是純粹的新增欄位或新增參數，屬於非破壞性
變更，因此現在不預留欄位——預留只會得到恆為 null 的死欄位，還會鎖死型別。

- **作者資訊**（識別字、顯示名稱、頭像）。這會推翻既有的「便條不帶 uuid 身分欄位」
  決定，需要先做「匿名 vs 具名」的產品決策並以新的 ADR 取代舊決定。若日後採用，
  上 wire 的識別字必須是獨立的公開 id，絕不能是認證系統的使用者 id。
- **撿起者資訊**。在收藏列表中永遠是自己（無資訊量），在自己的便條列表中揭露則會傷害
  撿起者的匿名性——他只是撿了一張便條，沒有選擇露臉。目前沒有讀者。
- **照片**。這是一個子系統而非欄位：需要儲存空間、上傳流程、EXIF 定位資訊剝除、
  公開儲存與簽章網址的取捨、使用者上傳圖片的審查（會讓檢舉機制從「上架前要有」升級為
  「有照片就必須有」）、以及流量成本。另有一條契約層硬性限制須一併設計：照片絕不可
  出現在探索提示中，否則在 100 公尺外就送出了內容，撿起機制失去意義。
- **便條狀態欄位**。目前僅有的兩個狀態都能從撿起時間推導，落地成欄位會產生兩個真相
  來源。等「限時可編輯」「自動過期」「檢舉隱藏」其中之一實際落地再加，且必須由伺服器
  推導而非儲存。
- **更新時間欄位**。便條目前不可變，此欄位會恆等於建立時間。
- **列表的 audience 過濾參數**。目前沒有「只看旅遊紀錄」的分頁需求；新增參數是非破壞
  變更，屆時再加，連同對應的索引調整。
- **API 版本化機制**（路徑或 header 版本）。有了未知值政策，可預見的未來用不到；
  真的需要破壞性變更時，開一支新函式名即可。
- **色票與樣式的實際內容**。對照表在裝置端，後端不需要知道，也不驗證。
- **部署到 hosted 專案、檢舉機制、便條自動過期**——各自為獨立任務。

## Further Notes

**這個設計唯一會損壞歷史資料的失效模式**：`color` 與 `style` 的數字必須被當作
**永久 ID**，而不是清單位置。對照表只能追加新項，既有代號的意義永久凍結；顯示順序是
呈現層的事，必須與代號身分脫鉤。若違反——例如設計在調色盤中間插入一個新顏色並讓後面
的項目順移——所有既有便條會靜默換色，而對照表在裝置端、後端看不到它變了，兩側都不會
產生任何錯誤訊號，等到旅人回報時已無原始資料可還原。後端在技術上無法對此把關，
只能靠紀律，因此必須寫在對照表文件的開頭，並在與 iOS 的交接中明確傳達。

**與既有決策的關係**：本次變更維持「撿起即獨佔消失」的語意與其單一謂詞實作，不引入
狀態欄位；維持「探索靠 client 前景輪詢、半徑為伺服器常數、client 不硬編門檻」的約定，
新形狀仍以伺服器計算的距離與可撿旗標傳達結果；維持「接受 client 自報座標」及其兩個
上限緩解措施。三份既有決策紀錄均不需修改。

**建議的實作順序**：資料模型與新欄位先落地並讓既有測試維持全綠，再逐一改造 RPC 的
回傳形狀，最後才是分頁與錯誤的機制變更；三份契約產出在 RPC 行為穩定後才同步改寫，
避免文件與實作互相追逐。

**驗收**：完成後依專案守則派獨立 subagent 做兩個視角的複核——安全審查（RLS 是否可繞過、
新欄位是否經由契約外的直讀路徑外洩、參數驗證、濫用防護）與正確性驗證（邊界條件、
游標平手情境、兩人同時撿同一張便條的併發情境）。複核者只拿本 spec，不繼承實作過程的假設。
